# 1. Auditor Role

This audit was performed as an independent external review of the AgentFlow Delivery Framework. No framework document, template, repository, process or implementation was modified during the audit. No author of the framework participated in forming the conclusions.

A documented rule was never treated as an implemented or enforced control. Every material capability was classified against the following scale:

| **Classification** | **Meaning as used in this report**                                                                       |
|--------------------|----------------------------------------------------------------------------------------------------------|
| DOCUMENTED         | The rule exists in a framework document.                                                                 |
| IMPLEMENTED        | The kit provides a concrete, usable artifact (template, token, checklist) that operationalises the rule. |
| ENFORCED           | Execution is mechanically prevented when the rule is not satisfied.                                      |
| VERIFIED           | The auditor observed the control operating on real work.                                                 |
| NOT VERIFIED       | The control may operate correctly, but no evidence was available to confirm it.                          |
| MISSING            | The capability does not exist in the framework in any form.                                              |

*Audit-wide observation: across the entire framework, no control reaches ENFORCED and none reaches VERIFIED, because the kit is a documentation artifact and no execution evidence was supplied. This is stated once here and is not repeated as a separate finding for each domain; it is captured as F-07.*

# 3. Scope — Domain Findings

## 3.1 Governance

Governance is the most developed part of the framework. Decision rights sit explicitly with a human owner or authorised approver; AI agents are defined as execution and decision-support participants that may not silently assume authority over scope, architecture, security, privacy, cost or release. The canonical phase/status taxonomy is complete and unambiguous, and the rule that "BLOCKED alone is not a canonical status" (use a phase-specific status plus Blocked by) is a genuinely mature detail that most lightweight processes omit.

Two defects were identified. First, Requirement Approval is declared a mandatory gate in Governance and in the Adoption Guide, yet the canonical token table defines tokens only for transfer, architecture, task contract and production — leaving the first gate of the process to be satisfied by exactly the kind of conversational agreement the framework elsewhere forbids. Second, approvals are defined as scoped tokens but the framework never states where a token must be recorded to count. A token issued in a chat session is not distinguishable, after the fact, from one recorded against an issue.

Separation of duties is deliberately weak in the default single_owner model, where one person approves requirement, architecture, task contract and production. For the declared target users this is an accepted trade-off rather than a defect, but it means the framework contains no independent check on the approver.

- Decision model, phase/status taxonomy and blocking semantics: DOCUMENTED and IMPLEMENTED.

- Explicit approval tokens: DOCUMENTED and IMPLEMENTED for 4 of 5 mandatory gates.

- Escalation paths (stop conditions, material-change escalation): DOCUMENTED, coherent, NOT ENFORCED.

**Related findings:** F-02, F-10, F-11, F-12, F-13

## 3.2 Requirements

The idea-to-requirement path is properly separated from implementation. The Requirement template captures problem, affected user, desired outcome, scope, out-of-scope, acceptance criteria, product invariants, constraints and open questions, and the status set matches the canonical taxonomy. The Development Transfer artifact carries only approved intent and explicitly prohibits prescribing new architecture, which is the correct boundary.

The weakness is at the approval boundary (F-02) rather than in the artifact itself. Additionally, acceptance criteria are free-text checkboxes with no requirement that each criterion be individually testable or later mapped to a specific test; the Evidence Bundle does ask for a criterion-to-evidence mapping, so the chain exists but its quality is entirely dependent on how the criteria were written.

- Requirement artifact: DOCUMENTED, IMPLEMENTED.

- Requirement approval gate: DOCUMENTED, token MISSING.

- Requirement-to-acceptance-criteria testability rule: MISSING.

**Related findings:** F-02

## 3.3 Architecture Governance

The Architecture Delta Check is the strongest single control in the framework. It enumerates concrete material-change triggers (persistence, data ownership, identity and authorisation, tenancy, component boundaries, shared contracts, orchestration and concurrency, provider or runtime with architectural role, security and privacy, material cost or portability) and prescribes a deterministic response: stop executable planning, mark the phase blocked, formulate the architecture question, evaluate options, obtain an approver decision, then revalidate the affected Development Analysis and ATCs. The revalidation step is what prevents architecture-by-implementation, and its presence is a mark of maturity.

The Architecture Decision Record template is complete (options, reversibility, what is given up, impact check, deferred items) and the rule that a material UNKNOWN blocks approval is a correct fail-closed construct at the artifact level.

One inconsistency: the ADR template uses a status vocabulary (PROPOSED / ACCEPTED / SUPERSEDED) that does not exist in the canonical taxonomy (ARCHITECTURE_REVIEW / ARCHITECTURE_READY_FOR_APPROVAL / ARCHITECTURE_APPROVED / ARCHITECTURE_CHANGES_REQUIRED / ARCHITECTURE_BLOCKED). Two vocabularies for the same artifact will diverge in practice and defeat automated status reading later.

- Architecture Delta Check: DOCUMENTED, IMPLEMENTED, NOT ENFORCED — detection depends on the executing agent choosing to run the check.

- Post-decision revalidation of Development Analysis and ATCs: DOCUMENTED — a notable strength.

**Related findings:** F-13, F-07

## 3.4 Development Analysis

Development Analysis is correctly defined as read-only with respect to product and runtime state, with a required output set (verified baseline, affected components, dependencies, Architecture Delta Check, slicing, risks, proposed ATCs, stop conditions, verdict) and a single positive verdict, READY_FOR_TASK_CONTRACTS. The statement that Development Analysis does not authorise implementation is explicit and repeated.

Gaps are quality-related rather than structural. "Verified technical baseline" is not defined — there is no minimum standard for what constitutes verification of a baseline, and no requirement to record what was inspected. An agent may therefore produce a confident analysis from an unverified reading of the repository and remain formally compliant. There is also no template for the Development Analysis output itself; the kit supplies templates for Requirement, Transfer, ADR, ATC, Evidence, Review, Release Record and Executable Task, but the analysis that generates the ATCs has no artifact of its own.

- Read-only boundary and output set: DOCUMENTED.

- Development Analysis artifact/template: MISSING from the kit.

- Baseline verification standard: MISSING.

**Related findings:** F-01

## 3.5 Agent Task Contract

The ATC is well constructed and is the correct unit of control for AI execution. It carries a stable identity, parent references, objective, scope, out-of-scope, required context, candidate components, dependencies, constraints, acceptance criteria, tests, retry limit, stop conditions and required evidence, and it becomes executable only on approval of that exact reference. The required-context and excluded-context concepts materially reduce the most common AI failure mode, which is unbounded context leading to unbounded change.

Two issues. The kit ships a second template, EXECUTABLE-TASK.md, that covers substantially the same ground with no rule stating when each is used; it is absent from the recommended repository structure in the usage guide and from the minimum adoption set in the README, while appearing in the manifest. Its status is genuinely ambiguous. Separately, the ATC has no declared maximum size or decomposition rule beyond the guidance that it must be "small enough for independent review", which is not measurable.

- ATC field set: DOCUMENTED, IMPLEMENTED, sufficient.

- Scoped approval per exact ATC reference: DOCUMENTED, IMPLEMENTED, NOT ENFORCED.

- ATC sizing rule: DOCUMENTED but not measurable.

**Related findings:** F-16, F-07

## 3.6 Agent Execution Controls

The execution control set is coherent: implement only the approved ATC, preserve architecture and existing contracts, no opportunistic refactoring, no unapproved material dependencies, no deletion of functionality outside scope, prefer reversible local decisions, bounded self-correction, stop on defined stop conditions. The Implementation Preservation Rule is an unusually precise expression of "approval of an outcome is not approval of a mechanism", and the instruction not to escalate purely local, reversible, in-scope decisions prevents the opposite failure of escalation paralysis.

The retry model is bounded within one execution cycle (default two self-correction cycles) but unbounded across cycles. Review remediation is defined as a new implementation cycle, and TEST failure returns to DEV for a new candidate, with no limit on how many such loops may occur before the item is escalated back to Requirement or Architecture. In AI-assisted delivery this is the classic failure mode: repeated plausible fixes to a problem whose real cause is an underspecified requirement.

Ambiguity handling is defined by category (the stop-condition list) rather than by a confidence threshold, which is the right choice for a tool-neutral framework.

- Scope control, no opportunistic refactoring, dependency control: DOCUMENTED, NOT ENFORCED.

- Per-execution retry limit: DOCUMENTED, IMPLEMENTED.

- Cross-cycle loop limit and escalation: MISSING.

**Related findings:** F-17, F-07

## 3.7 Evidence

Evidence is conceptually the centre of the framework — "prove what was executed" is one of its six principles — and the Evidence Bundle template covers identity, files changed, checks with results, acceptance-criteria mapping, assumptions, deviations, known limitations, residual risks, retry history and verdict. The rule that evidence must permit verification without reconstructing conversation history is correct and is the right standard.

The control nevertheless has a structural weakness: evidence is produced by the executor, in free text, with no requirement that any item be independently reproducible or externally attested. The framework tells the agent not to claim a check it did not perform, and gives good examples of invalid inference (a build passing does not prove deployment; UI observation does not prove an HTTP status), but an instruction not to fabricate is not a control against fabrication. Nothing in the template requires a CI run reference, a log artifact, a test-report file, a command transcript or a reviewer-reproducible command. The entire downstream chain — Independent Review, TEST scoping, PROD GO — rests on evidence whose integrity is assumed.

Candidate identity within the bundle is handled correctly: the bundle carries the PR/commit/candidate reference, and the framework states that TEST PASS on candidate A does not apply to candidate B.

- Evidence artifact and required content: DOCUMENTED, IMPLEMENTED.

- Evidence integrity / reproducibility requirement: MISSING.

- Evidence-to-acceptance-criteria mapping: DOCUMENTED, IMPLEMENTED.

**Related findings:** F-01, F-04

## 3.8 Independent Review

Review is correctly modelled as a comparison of three fixed inputs — approved ATC, exact implementation candidate, Evidence Bundle — with three verdicts and precise semantics: FAIL for demonstrated non-conformance, BLOCKED when validation cannot be completed. The prohibition on repairing the implementation within the same review step is stated in three separate documents and is one of the framework's better design decisions, because it prevents the self-certifying loop in which an agent fixes and then declares conformance.

Two material gaps. First, independence is asserted but never defined. The Project Adapter asks the project to state a "reviewer model" and "required independence", and the Adoption Guide says independence should remain "meaningful", but Core sets no minimum: it does not require a different agent instance, a separate session, absence of the executor's context, or a different human. For a framework whose premise is that AI executes most work, an undefined independence criterion means review independence can be nominal.

Second, the review verdict is not bound to a candidate identity. Rule 6 of the delivery lifecycle invalidates the previous TEST result when a source change creates a new candidate, and the AI execution rules say a post-freeze change "requires DEV/TEST again" — review is not mentioned. Since review occurs before candidate freeze in the nominal flow, a REVIEW_PASS can legitimately refer to code that no longer exists by the time the candidate is frozen, and nothing in the framework detects this.

- Review inputs, verdicts and no-repair rule: DOCUMENTED, IMPLEMENTED.

- Reviewer independence criterion: MISSING from Core.

- Review-to-candidate binding and invalidation: MISSING.

**Related findings:** F-03, F-06

## 3.9 DEV / TEST / PROD Lifecycle

The release lifecycle is the most operationally mature component. The invariant DEV candidate = TEST candidate = PROD candidate, candidate freeze on an immutable source identity, the prohibition on fixing in TEST, invalidation of TEST results by any post-freeze source change, rollback known before production mutation, explicit PROD GO scoped to the candidate reference, smoke validation and a Release Record together form a complete and internally consistent release control set. Destructive data changes are handled better than in many enterprise processes: backup, integrity evidence and a demonstrated non-production restore are required before production.

Three gaps were identified. Candidate composition is never verified: the Release Record links one requirement and one candidate, but a real candidate is typically an integration of several merged changes, and no control requires proof that every change contained in the promoted candidate has an approved ATC and a passing review. The framework states that merge does not authorise deployment, but nothing checks what the merge brought in.

The hotfix path reduces controls further than the framework acknowledges. It is defined as scope, DEV, freeze, targeted TEST, rollback check, PROD GO, PROD — with no ATC, no Evidence Bundle and no Independent Review, and the only explicit acceptance required is for reduced test breadth. The most dangerous path in the lifecycle is therefore the least controlled.

Finally, production failure handling assumes rollback is feasible ("execute predefined rollback when applicable") without defining a gate for the case where it is not; forward-fix under production pressure is precisely where unauthorised change enters, and it is unaddressed.

- Candidate immutability and identity invariant: DOCUMENTED, IMPLEMENTED, NOT ENFORCED.

- Independent TEST on the exact candidate: DOCUMENTED.

- Rollback-before-PROD including destructive data changes: DOCUMENTED, strong.

- Candidate composition proof: MISSING.

- Hotfix control set: partially MISSING by design.

**Related findings:** F-04, F-05, F-20, F-03

## 3.10 Documentation / Source of Truth

The documentation policy is well conceived. The L0–L3 layering, progressive context loading, the Context Map with required/optional/excluded context, the separation of current state from history, and the safeguard questions before creating a new document address the real operational problem of agent-assisted work, which is context volume rather than context absence. The source-of-truth hierarchy correctly ranks repository state above conversation memory and approved canonical architecture above an agent's preferred redesign, and the instruction to record a CONFLICT rather than resolve it silently is a deterministic and correct rule.

The framework does not, however, apply its own policy to itself. The end-to-end process flow is stated five times, in the README, Governance, the AgentFlow operating contract, the Delivery Lifecycle and the Romanian usage guide, and the versions are not identical: the transfer approval appears in one and not the others, and the usage guide introduces a "RELEASE READY" step that exists in the canonical status taxonomy but not in the other flow diagrams. There is no single normative process definition, which is the exact condition the policy prohibits.

Auditability is also limited by the absence of a defined location for approval records and by the absence of document ownership, which the bootstrap procedure checks for in target projects but Core never defines for itself.

- L0–L3 layering, progressive context, Context Map: DOCUMENTED, IMPLEMENTED — a differentiating strength.

- Source-of-truth precedence rules: DOCUMENTED.

- Single canonical process definition: MISSING (self-violation).

- Approval record location / audit trail: MISSING.

**Related findings:** F-08, F-10, F-25, F-27

## 3.11 Security and Privacy

Security coverage is limited to three mechanisms: security, privacy and secrets are architecture-gate triggers; secrets are prohibited in source, documentation, stored prompts, client bundles and committed fixtures, with a prohibition on inventing production-like credentials; and security or privacy concerns requiring explicit acceptance are stop conditions. These are correct as far as they go, and the deliberate exclusion of a full secure-SDLC programme from Core is a defensible scoping decision.

The material omission for an AI-native framework is not the absence of SAST, DAST, SBOM or dependency scanning — those are legitimately adapter concerns — but the absence of any control over adversarial input to the executing agent. An agent operating under an ATC reads issue text, repository content, dependency documentation and tool output, any of which may contain instructions. The framework contains no rule that content encountered during execution is data rather than instruction, no requirement that a change in scope originate from an approved artifact, and no privilege boundary defining what credentials an executing agent may hold. Nothing in Core prevents the same agent identity from holding production credentials while executing a DEV-scoped ATC.

Privacy handling of data is also unaddressed: there is no rule governing production data copied into DEV or TEST environments, which is a routine requirement in European contexts.

- Secrets handling rules: DOCUMENTED.

- Security/privacy as architecture triggers and stop conditions: DOCUMENTED.

- Adversarial-input / instruction-provenance control for agents: MISSING.

- Agent privilege boundary and credential scoping: MISSING.

- Secure SDLC (threat modeling, SCA, SAST, DAST, SBOM), security acceptance gate: MISSING (adapter-appropriate).

**Related findings:** F-09, F-21, F-22

## 3.12 Operational Model

The lifecycle terminates at smoke validation and Release Record completion. Rollback is well covered, and the production-failure path (stop, roll back, verify restored identity, preserve evidence, fix in DEV, new candidate) is correct.

Everything after that moment is absent: there is no post-release observation window, no monitoring or alerting expectation, no service-level objectives or error budgets, no operational ownership hand-off, no capacity or cost control, and no incident lifecycle. The Definition of Done therefore closes an item at the point where operational risk begins. For solo and small-team projects this is an acceptable boundary provided the owner is also the operator; for any project with users depending on availability it is a real gap, and it should be delivered as an operations adapter rather than added to Core.

- Rollback and production-failure handling: DOCUMENTED, IMPLEMENTED.

- Post-release observation, monitoring, SLI/SLO, incident lifecycle, operational ownership: MISSING.

**Related findings:** F-19

## 3.13 Multi-Agent Readiness

The framework separates roles conceptually (architect, analyst, executor, reviewer, QA, approver) and forbids an agent assigned to one stage from silently executing the next, which is the correct foundation. It does not, however, provide the mechanics that multi-agent operation requires.

There is no agent identity model: the Evidence Bundle carries a free-text "Executor" field with no requirement to record which agent, model, version or session produced the work, so provenance of AI-generated change is not reconstructable. There is no task locking, no concurrency rule, no duplicate-execution detection, no formal handoff artifact between stages, and no recovery procedure when an agent abandons or fails mid-ATC — the item would simply remain in an implementing status with no owner and no timeout.

This is correctly identified as future work by the framework itself. It is restated here as an audit finding because the framework is named and positioned around agents, and a reader may reasonably assume multi-agent coordination is in scope.

- Stage-boundary separation: DOCUMENTED.

- Agent identity and provenance: MISSING.

- Locking, concurrency, duplicate detection, handoff protocol, abandonment recovery: MISSING.

**Related findings:** F-18

## 3.14 Portability

Portability is genuinely achieved and is one of the framework's clearest strengths. Core defines no dependency on GitHub, a specific CI or CD engine, a cloud provider, a database, an AI vendor or a project structure; platform names are confined to the Project Adapter and the configuration file, the non-goals section explicitly rejects Scrum, SAFe, ITIL, CAB and vendor integration, and candidate identity permits an alternative immutable artifact where source identity cannot be promoted directly. The audit found no hidden coupling to the originating project.

Two residual assumptions are worth stating. Core assumes the existence of a promotable immutable identity and a review-and-merge source-control model, which fits git-based delivery well but fits low-code platforms, SaaS configuration changes and store-distributed mobile binaries only partially. It also assumes read access sufficient for an agent to inspect repository and delivery tooling during bootstrap, which is not always available in restricted environments. Neither is a defect; both should be stated as preconditions.

- Core independence from tools, providers, models and project structure: DOCUMENTED and substantiated.

- Adapter layering (Project Adapter, configuration file): DOCUMENTED, IMPLEMENTED.

- Declared preconditions for applicability: MISSING.

**Related findings:** F-26, F-15

# 4. Out of Scope

# 7. Required Challenge Scenarios

## Scenario 1 — Scope Creep

**Situation:** During implementation, an agent identifies an adjacent improvement.

**Audit question:** Does AgentFlow reliably prevent silent inclusion?

**Result:** CONTROLLED BY DESIGN, NOT PREVENTED MECHANICALLY

Three independent rules address this: the ATC out-of-scope field, the No Opportunistic Refactoring rule, and the Implementation Preservation Rule, which states that approving an outcome does not approve changes to boundaries, contracts, persistence, identity, orchestration, providers, dependencies or established semantics. Independent Review checks "out of scope preserved" as a distinct conformance line, and the Evidence Bundle requires deviations to be declared. This is a genuinely strong design. What is missing is detection: if the executor neither declares the deviation nor lists the touched file, review has no independent source against which to notice it, because the file list and the evidence both originate from the executor (F-01).

## Scenario 2 — Architecture Change Discovered During DEV

**Situation:** Implementation requires a new datastore, shared API contract or architectural boundary change.

**Audit question:** Does execution stop and return to Architecture?

**Result:** YES — strongest control path

This is an explicit stop condition and an explicit architecture trigger, with a prescribed sequence: stop, mark the phase blocked, produce evidence, escalate to the architecture gate, obtain an approver decision, then revalidate Development Analysis and the affected ATCs. The revalidation step closes the loop that most processes leave open. Residual risk is detection-side only: the trigger list is material-change-based and an agent that misclassifies a change as immaterial will not stop. No second-line check exists.

## Scenario 3 — Missing Approval

**Situation:** An ATC exists but has not been explicitly approved.

**Audit question:** Can implementation proceed?

**Result:** PROHIBITED BUT NOT PREVENTED

The rule is unambiguous and stated in four documents, including the instruction never to infer approval from generic conversational language. However, no component evaluates authorisation state before execution; compliance is behavioural. An agent that misreads intent, or a user who says "just do it", produces unauthorised implementation with no artifact recording that a gate was skipped. For the first gate of the process — Requirement Approval — the position is worse, because no token is defined at all (F-02).

## Scenario 4 — Retry Exhaustion

**Situation:** Mandatory tests still fail after configured retry limits.

**Audit question:** Does the process fail closed?

**Result:** YES WITHIN THE CYCLE, NO ACROSS CYCLES

Within one execution the rule is correct and explicit: after the retry limit, stop speculative patching, record evidence and return a blocked or failed verdict. Across cycles there is no limit. Review remediation creates a new implementation cycle and TEST failure returns to DEV for a new candidate, indefinitely. Nothing triggers escalation to Requirement or Architecture after repeated failures on the same item, which is precisely the pattern that indicates an underspecified requirement rather than a coding defect (F-17).

## Scenario 5 — Reviewer Discovers a Defect

**Situation:** Review identifies non-conformance.

**Audit question:** Is review clearly separated from remediation?

**Result:** YES — separation is explicit and consistent

The prohibition on repairing during review is stated in the operating contract, the AI execution rules and the review template, and the verdict semantics distinguish demonstrated non-conformance (FAIL) from inability to validate (BLOCKED), which is a distinction many processes collapse. The weakness is upstream: who the reviewer is, and how independent they must be, is left entirely to the project (F-06). With a single agent and a single owner, separation of activity is preserved while separation of judgement may not be.

## Scenario 6 — Candidate Mutation After TEST

**Situation:** Code changes after TEST PASS.

**Audit question:** Is previous TEST evidence invalidated?

**Result:** YES for TEST — NO for REVIEW

Invalidation of TEST is explicit and correct: any source change after freeze creates a new candidate identity, invalidates the previous TEST result and requires DEV and TEST again; the framework also states that TEST PASS on candidate A does not apply to candidate B. The same rule is never extended to the Independent Review verdict, which in the nominal flow is produced before candidate freeze. A promoted candidate can therefore carry a review verdict that refers to earlier code, and neither the Release Record nor the PROD gate requires the review reference to be re-confirmed against the final candidate identity (F-03).

## Scenario 7 — PROD Failure

**Situation:** Smoke validation fails after deployment.

**Audit question:** Is rollback predetermined and is remediation returned to DEV?

**Result:** YES, with one unhandled branch

Rollback must be known before production mutation, the previous production identity must be captured, and the failure path is prescribed: stop, roll back where applicable, verify restored identity and health, preserve evidence, fix in DEV, create a new candidate, and repeat the full promotion. Ad-hoc production patching is explicitly forbidden. The unhandled branch is the case where rollback is not applicable or not feasible; the framework qualifies rollback with "when applicable" but provides no authorisation gate, evidence requirement or decision record for forward-fix under production pressure (F-20).

## Scenario 8 — Documentation Conflict

**Situation:** Repository state contradicts canonical architecture documentation.

**Audit question:** Does the framework provide a deterministic handling rule?

**Result:** YES

The rules are precise and correctly ordered: repository state outranks conversation memory as evidence of implementation; approved canonical architecture outranks an agent's preferred redesign; a material conflict between code and approved documentation is recorded as CONFLICT and must not be resolved silently; superseded material is not current merely because it exists. This is one of the few places where the framework prescribes behaviour that is both deterministic and hard to rationalise away. It does not, however, say who owns resolution or within what period, so a CONFLICT can persist indefinitely.

## Scenario 9 — Multi-Agent Collision

**Situation:** Two agents attempt overlapping work.

**Audit question:** NOT PREVENTED

**Result:** NOT PREVENTED

Nothing in the framework prevents or resolves this. There is no task locking, no assignment semantics, no concurrency rule and no duplicate-work detection. Two ATCs derived from the same Development Analysis may touch the same components with no declared conflict. The partial mitigations are indirect: ATC scoping and candidate-file declarations make a collision visible after the fact, and merge conflicts surface at integration. Detection, not prevention (F-18).

## Scenario 10 — Adoption in Another Project

**Situation:** AgentFlow is applied to an unrelated repository.

**Audit question:** Which Core rules transfer directly and which require adapters?

**Result:** TRANSFERS CLEANLY

Transferring directly: approval discipline and token semantics, Architecture Delta Check, Development Analysis boundary, ATC structure, retry and stop conditions, Evidence Bundle content, review verdict semantics, candidate immutability, rollback-before-PROD, source-of-truth hierarchy, progressive context loading. Requiring adapter values: environment mapping, candidate identity mechanism, branch and merge rules, CI and CD engines, issue tracker, reviewer model, project-specific architecture triggers, rollback mechanism, documentation map. Requiring an organisation adapter: security and compliance gates, multi-approver chains, audit retention, change classification. The bootstrap procedure operationalises exactly this separation and is, in the auditor's assessment, the most complete single document in the kit.

# 9. Audit Output

## 9.1 Executive Summary

AgentFlow is a coherent, well-scoped and genuinely reusable governance and delivery protocol for AI-assisted software work. Its central design decision — separating the authority to decide from the capacity to execute, and forcing execution through an explicitly approved contract with declared evidence — is correct, and it is carried consistently through requirements, architecture, development analysis, execution, review and release. The framework avoids the two common failure modes of this category: it neither reduces to prompting advice nor inflates into enterprise process ceremony. The audit found no hidden dependency on the project it originated from.

Its principal limitation is not a missing rule but a missing layer. Every control in AgentFlow is satisfied by an agent choosing to satisfy it. There is no component that evaluates authorisation state, validates an artifact, or refuses a transition, and the framework does not itself claim otherwise. The consequence is that AgentFlow reliably prevents accidental process violations by a cooperative agent and a disciplined owner, and does not prevent violations by an agent that is confidently wrong — which is the dominant real-world failure mode of AI execution. Two specific chains inherit this weakness: evidence is produced by the same actor whose work it attests, and the review verdict is not bound to the candidate identity that is eventually promoted.

Strongest controls:

- Architecture Delta Check with mandatory revalidation of Development Analysis and ATCs after an architecture decision.

- Implementation Preservation Rule and No Opportunistic Refactoring — precise, enforceable-by-review scope protection.

- Candidate immutability with the DEV = TEST = PROD identity invariant and explicit invalidation of TEST on any post-freeze change.

- Scoped, non-inferable approval tokens with an explicit rejection of conversational approval.

- Separation of review from remediation, with FAIL and BLOCKED semantics distinguished.

- Rollback-before-PROD, including backup, integrity evidence and demonstrated non-production restore for destructive data change.

- Documentation policy with L0–L3 layering and progressive context loading — the best answer in the kit to the context-volume problem of agent work.

- The bootstrap procedure: read-only by default, verdict-based, with explicit UNKNOWN handling and no silent conversion of existing work.

Largest risks:

- Self-attested evidence: the assurance chain rests on unverifiable statements by the executor (F-01).

- No enforcement layer: every gate is advisory to the agent that must respect it (F-07).

- Review verdict can become stale relative to the promoted candidate (F-03).

- Candidate composition is never proven to contain only approved, reviewed work (F-04).

- Hotfix drops ATC, evidence and review while retaining the appearance of process compliance (F-05).

- Reviewer independence is required in name and undefined in substance (F-06).

- No control over adversarial or untrusted content reaching an executing agent (F-09).

- Requirement approval — the first gate — has no token (F-02).

Currently suitable for: solo and small-team delivery with a single accountable owner; AI-assisted development where architecture must be protected from incremental drift; products with real DEV, TEST and PROD environments and a git-style immutable candidate; organisations piloting agent governance before committing to tooling; existing projects needing graduated adoption without mass conversion.

Not sufficient without extensions for: regulated or audited delivery, where approval records and evidence must be durable and independently verifiable; multi-team or multi-agent concurrent delivery; production services requiring operational and incident management; autonomous execution with reduced human presence at gates, which is the one context where the absence of enforcement becomes load-bearing.

## 9.4 Findings

Ordered by severity, then by dependency and execution priority.

### F-01 — Evidence is self-attested and not required to be independently reproducible

| **Domain** | **Severity** | **Type**    | **Required before** |
|------------|--------------|-------------|---------------------|
| Evidence   | HIGH         | CONTROL_GAP | NEXT_MINOR          |

**Evidence:** The Evidence Bundle template accepts free-text results in every column ("Check / Result / Evidence"), and the required-evidence list in the operating contract and the ATC template names content categories, not artifact types. No field requires a CI run reference, a log or test-report artifact, a command transcript or a reproducible verification command. The AI execution rules prohibit claiming an unperformed check and give correct examples of invalid inference, but that is an instruction, not a control.

**Why it matters:** Evidence is the load-bearing element of the framework: Independent Review, TEST scoping and PROD GO all consume it, and the stated standard is that evidence must permit verification without reconstructing the conversation. If the evidence itself is unverifiable prose, the review verifies a narrative rather than an execution, and every downstream assurance inherits that weakness. This is the single point where "prove what was executed" is asserted but not secured.

**Failure scenario:** An agent reports all tests passing, maps each acceptance criterion to a plausible description, and records no deviations. Review finds full formal conformance. DEV verification is light because evidence says the work is complete. The defect surfaces in TEST at best, in production at worst, and the Evidence Bundle contains no artifact that would have revealed it.

**Recommendation:** Introduce an evidence class model in Core: ATTESTED (executor statement), ARTIFACT (externally produced output referenced by location and identity), REPRODUCIBLE (a command or pipeline the reviewer can re-run). Require every mandatory check in an ATC to be satisfied at ARTIFACT level or above, and require the Evidence Bundle to record the artifact reference. Add an Evidence Bundle field "Independently reproducible: YES / NO / PARTIAL", and make Independent Review return BLOCKED rather than PASS where a mandatory check is ATTESTED only.

### F-02 — Requirement Approval is a mandatory gate with no defined approval token

| **Domain**                | **Severity** | **Type**    | **Required before** |
|---------------------------|--------------|-------------|---------------------|
| Governance / Requirements | HIGH         | CONTROL_GAP | NOW                 |

**Evidence:** Governance declares explicit Requirement Approval in the nominal flow and lists REQUIREMENT_APPROVED as a canonical status; the Adoption Guide lists Requirement Approval among the minimum gates for even a solo project. The token table defines only APPROVE_TRANSFER, APPROVE_ARCHITECTURE, APPROVE_TASK_CONTRACT and PROD_GO. The Requirement template records approval as free-text Decision / Approved by / Date. The configuration example contains no requirement token.

**Why it matters:** The framework's own rule is that generic phrases such as "ok", "go", "looks good" must not change authorisation state where a token is required. By omitting a token for the first gate, the framework permits exactly that ambiguity at the point where scope is established — and every later gate inherits an unverifiable premise about what was approved.

**Failure scenario:** An owner responds "yes, that's what I want" to a requirement draft. The agent sets REQUIREMENT_APPROVED, transfers to Development Analysis and produces ATCs. Three ATCs later, the owner disputes a scope item. No record exists of what was approved or when, because approval was conversational.

**Recommendation:** Add APPROVE_REQUIREMENT \<ref\> to the canonical token table, the FRAMEWORK-CONFIG defaults, the configuration example under approval.tokens, and the Requirement template approval section. Cost is trivial; it closes the only unprotected mandatory gate.

### F-03 — The Independent Review verdict is not bound to a candidate identity and is never invalidated

| **Domain**       | **Severity** | **Type**    | **Required before** |
|------------------|--------------|-------------|---------------------|
| Review / Release | HIGH         | CONTROL_GAP | NOW                 |

**Evidence:** The nominal flow places Independent Review before DEV verification and candidate freeze. Invalidation rules name only TEST: any source change after freeze creates a new candidate and invalidates the previous TEST result; the AI execution rules state that a post-freeze change "requires DEV/TEST again". Review is absent from every invalidation rule. The Release Record captures DEV and TEST evidence and the candidate identity but does not require a review reference tied to the final candidate.

**Why it matters:** The framework is otherwise rigorous about identity: TEST PASS on candidate A explicitly does not apply to candidate B. Review is granted an exemption it was never meant to have. The control that verifies contract conformance can therefore attach to code that was subsequently changed, and no artifact in the chain records the mismatch.

**Failure scenario:** REVIEW_PASS is issued. DEV verification finds a failing test; the executor fixes it — legitimately, inside ATC scope. The candidate is frozen at the new SHA, passes TEST, and is promoted. The promoted candidate has never been reviewed against the approved contract, and the Release Record looks complete.

**Recommendation:** Bind the review verdict to a candidate identity: record REVIEW_PASS against a specific commit or candidate reference, extend the invalidation rule to read "any source change after review invalidates the review verdict for the superseded identity", and add "Reviewed candidate ID" to the Release Record with a PROD-gate check that it equals the promoted candidate. Permit a bounded delta re-review rather than a full re-review where the change is confined to previously reviewed scope.

### F-04 — Candidate composition is never verified against approved and reviewed work

| **Domain**             | **Severity** | **Type**         | **Required before** |
|------------------------|--------------|------------------|---------------------|
| Release / Traceability | HIGH         | TRACEABILITY_GAP | NEXT_MINOR          |

**Evidence:** The Release Record identifies one requirement, one implementation reference and one candidate ID. The lifecycle states that merge or integration does not itself authorise deployment, but no gate requires an inventory of what the candidate contains. G4 requires that the TEST-passed candidate is the one promoted and that identity was not rewritten — it does not require that every change inside that identity is approved.

**Why it matters:** In any real repository a candidate is an integration of multiple merges. The framework protects the identity of the container while leaving its contents unverified. Every upstream control — ATC approval, review, architecture gate — can be fully satisfied for the tracked work item while unrelated or unapproved change rides into production inside the same candidate.

**Failure scenario:** ATC-14 is approved, implemented, reviewed and frozen as a candidate off a main branch that has meanwhile received an unreviewed change. TEST validates the candidate's expected behaviour, which is unaffected. PROD_GO is issued against the candidate ID. The unapproved change reaches production having passed every gate without ever being examined.

**Recommendation:** Add a candidate manifest to G2: the set of work items, ATC references and review verdicts contained in the candidate relative to the previous production identity, plus an explicit statement of anything present that is not covered by an approved ATC. Make PROD GO conditional on the manifest containing no uncovered change, or on explicit owner acceptance of it. This is mechanisable later as a commit-range-to-ATC check.

### F-05 — The hotfix path drops ATC, Evidence Bundle and Independent Review

| **Domain** | **Severity** | **Type**    | **Required before** |
|------------|--------------|-------------|---------------------|
| Release    | HIGH         | CONTROL_GAP | NOW                 |

**Evidence:** The hotfix sequence is defined as scope, DEV, freeze candidate, targeted TEST, rollback check, explicit PROD GO, PROD. It states that urgency may reduce test breadth but not the core controls, and requires explicit approver acceptance of reduced test scope. It makes no reference to a Task Contract, an Evidence Bundle or an Independent Review, and no reference to which controls are considered core.

**Why it matters:** Hotfixes are executed under time pressure, on production-impacting defects, frequently by the agent that is most convinced it understands the problem. Removing contract boundaries and independent verification precisely there inverts the framework's own risk logic. The reduced path is also formally compliant, so nothing signals that a lower assurance level was used.

**Failure scenario:** A production defect is hotfixed. The agent, unbounded by an ATC, also adjusts an adjacent code path it considers related. There is no out-of-scope declaration, no evidence bundle and no reviewer. Targeted TEST covers the reported defect only. The adjacent change reaches production unexamined, during an incident, when attention is lowest.

**Recommendation:** Define a mandatory minimum hotfix control set in the lifecycle: a reduced ATC (objective, scope, out-of-scope, stop conditions) even if approved verbally and recorded after the fact; a reduced Evidence Bundle (files changed, checks run, deviations); and either an independent review or an explicit, recorded owner acceptance that review was waived, with a mandatory post-incident review of the hotfix candidate. State explicitly which controls may never be reduced: scope declaration, candidate identity, rollback, PROD GO.

### F-06 — Reviewer independence is required but never defined

| **Domain** | **Severity** | **Type**   | **Required before** |
|------------|--------------|------------|---------------------|
| Review     | HIGH         | DESIGN_GAP | NEXT_MINOR          |

**Evidence:** Core requires independent review and prohibits repair during review, but sets no independence criterion. The Adoption Guide states that one person may hold multiple roles if risk policy allows while review and test independence "should remain meaningful". The Project Adapter asks the project to supply a "reviewer model" and "required independence" with no menu of acceptable values and no minimum.

**Why it matters:** In AI-heavy use the reviewer is usually another agent, and independence is a property of the configuration, not of intent: the same model in the same session with the same context will reproduce the executor's reasoning, including its errors. Without a defined minimum, a project can satisfy the wording of the framework while obtaining no independent judgement at all — and the framework provides no way to detect this.

**Failure scenario:** Executor and reviewer are the same agent in the same session. The review reads the evidence the agent itself wrote, finds it consistent with the contract it itself interpreted, and returns REVIEW_PASS. Every artifact is present and correct. No independent verification occurred.

**Recommendation:** Define graded independence levels in Core and require the adapter to select one: L1 separate session with no executor context; L2 separate agent or model; L3 different human. Require the Evidence Bundle or review record to state the level used, prohibit L0 (same session, same context) for any ATC touching architecture, security, data or production behaviour, and require the reviewer to work from the ATC and candidate rather than from the executor's narrative.

### F-07 — No fail-closed enforcement layer: all gates depend on voluntary compliance

| **Domain**               | **Severity** | **Type**        | **Required before** |
|--------------------------|--------------|-----------------|---------------------|
| Automation / Enforcement | HIGH         | ENFORCEMENT_GAP | NEXT_MAJOR          |

**Evidence:** No component in the kit evaluates phase, status, required artifacts or authorisation state. Control tokens are defined as text conventions. Automated enforcement appears only as an optional post-bootstrap integration item (CI policy checks, branch and release safeguards), with no schema, reference implementation or minimum check set. The configuration file is descriptive; nothing consumes it.

**Why it matters:** The framework governs actors — AI agents — whose characteristic failure is confident, fluent non-compliance rather than refusal. Advisory gates work against accident and against a cooperative executor; they do not work against an agent that believes it is helping. Every other finding in this report is amplified by this one, because there is no second line that catches a first-line lapse.

**Failure scenario:** An agent under time pressure from the user interprets "let's get this out today" as sufficient authorisation, implements without an approved ATC, produces a well-formed Evidence Bundle after the fact, and promotes. Every artifact exists, every document is satisfied on its face, and no mechanism ever evaluated whether the token existed.

**Recommendation:** Introduce a machine-readable state and a minimum policy check set: a work-item state file or issue-field convention (process, phase, status, blocked-by, approvals with references), plus a small validator that answers "which gate is next, which artifacts are missing, is this transition permitted". Start with three CI checks that are cheap and high-value: no merge to the protected branch without an approved ATC reference; no candidate freeze without a review verdict bound to that SHA; no production deployment without a PROD_GO record naming that exact candidate. This is the framework's next maturity threshold and the correct centre of gravity for v2.

### F-08 — Five non-identical canonical process flows — the framework violates its own single-source rule

| **Domain**    | **Severity** | **Type**          | **Required before** |
|---------------|--------------|-------------------|---------------------|
| Documentation | HIGH         | DOCUMENTATION_GAP | NEXT_MINOR          |

**Evidence:** The end-to-end flow is stated in the README, in Governance, in the AgentFlow operating contract, in the Delivery Lifecycle and in the Romanian usage guide. They are not identical: the transfer approval appears in the operating contract as conditional and is absent from the README and usage-guide flows; the usage guide inserts a RELEASE READY step that the other diagrams omit; the README flow omits the evidence-to-review ordering nuance present in the operating contract. The documentation policy prohibits multiple current sources of truth and instructs authors to link rather than duplicate.

**Why it matters:** Drift has already occurred across five copies in a v1.1.0 kit maintained by its own author. It will accelerate once projects fork the kit, and it defeats the future state machine: there is no document that can be designated normative for transitions without first reconciling the five.

**Failure scenario:** A project implements CI checks from the README flow. An agent follows the usage-guide flow. An auditor evaluates against Governance. All three believe they are compliant with AgentFlow, and the item that skipped the transfer gate is not detected by anyone.

**Recommendation:** Designate one normative process definition — a transition table with phase, entry condition, required artifacts, exit gate, token and owner — in Governance or a new PROCESS-MODEL document. Replace every other flow diagram with a link and, at most, a simplified non-normative illustration explicitly marked as such. Remove flow diagrams from translated guides entirely.

### F-09 — No control over untrusted or adversarial content reaching an executing agent

| **Domain** | **Severity** | **Type**     | **Required before** |
|------------|--------------|--------------|---------------------|
| Security   | HIGH         | SECURITY_GAP | NEXT_MINOR          |

**Evidence:** The AI execution rules address secrets, evidence discipline, review independence and release protection. Nothing addresses the provenance of instructions. An executing agent reads issue text, repository files, dependency documentation, tool output and third-party content, and the framework contains no rule that such content is data rather than instruction, and no requirement that scope changes originate only from an approved artifact. The framework also sets no privilege boundary: nothing states which credentials an agent may hold for a given phase.

**Why it matters:** This is the AI-specific attack surface, and it is the one an AI-native framework should own rather than delegate. The Architecture Delta Check and the stop conditions assume the agent's judgement is merely fallible, not manipulated. An agent that holds production credentials while executing a DEV-scoped ATC has, in framework terms, no rule preventing it from acting on them.

**Failure scenario:** A dependency README, an issue comment or a file in the repository contains text instructing the agent to add an endpoint, disable a check or exfiltrate configuration. The agent, operating inside an approved ATC, treats it as context. The change is small, plausible and inside the touched component; the Evidence Bundle describes it as an implementation detail.

**Recommendation:** Add a short instruction-provenance rule to the AI execution rules: only the approved ATC and canonical documents referenced by it may alter scope or behaviour; all other content encountered during execution is data and must be treated as untrusted. Require any scope-affecting instruction found in project content to be escalated as a stop condition. Add a phase-scoped credential rule to the Project Adapter: which environments and secrets are reachable by the executing identity in each phase, with production credentials excluded from implementation phases by default.

### F-10 — Approval tokens have no defined durable recording location

| **Domain**                | **Severity** | **Type**         | **Required before** |
|---------------------------|--------------|------------------|---------------------|
| Governance / Traceability | MEDIUM       | TRACEABILITY_GAP | NEXT_MINOR          |

**Evidence:** Tokens are defined with precise semantics and scope, but no document states where a token must be recorded for it to be valid, who may record it, or how long it must persist. The Release Record asks for a "PROD GO reference" without defining what a valid reference is. The bootstrap procedure checks for issue and documentation conventions in the target project but does not require an approval-record location.

**Why it matters:** An approval that exists only in a chat session is not auditable and not transferable between agents or sessions — and the framework's own rule is that conversation history is context, not source of truth. Applied consistently, that rule means a token issued in conversation is not evidence of approval at all.

**Failure scenario:** Six months later the owner asks what authorised a production change. The Release Record references "PROD GO given". The session is gone. Nothing in the repository records the authorisation.

**Recommendation:** Require each project adapter to name a durable approval location (issue comment, PR review, signed record) and require every artifact that consumes an approval to carry a resolvable reference to it. Add "Approval record location" to the Project Adapter and to the bootstrap gap matrix.

### F-11 — APPROVE_AGENTFLOW_BOOTSTRAP sits outside the canonical token set and the configuration schema

| **Domain** | **Severity** | **Type**          | **Required before** |
|------------|--------------|-------------------|---------------------|
| Governance | MEDIUM       | DOCUMENTATION_GAP | NEXT_MINOR          |

**Evidence:** The bootstrap procedure and report define an owner gate using APPROVE_AGENTFLOW_BOOTSTRAP. Governance's token table, the framework configuration defaults and the configuration example's approval.tokens section do not contain it.

**Why it matters:** A real gate with real consequences — framework activation and subsequent write operations against the project — is governed by a token the governance model does not recognise. Any future validator built from the token list will not know it exists.

**Failure scenario:** A project generates its configuration from the example, sees four tokens, and treats bootstrap activation as informal. Framework artifacts are persisted into the repository without a recorded owner decision.

**Recommendation:** Add the bootstrap token to the canonical token table and to approval.tokens in the configuration example, with its scope stated: authorises persistence and activation of AgentFlow configuration, and nothing else.

### F-12 — Version incoherence between the kit and its Core documents

| **Domain**                 | **Severity** | **Type**          | **Required before** |
|----------------------------|--------------|-------------------|---------------------|
| Governance / Documentation | MEDIUM       | DOCUMENTATION_GAP | NEXT_MINOR          |
**Evidence:** The kit, the manifest, the bootstrap procedure and the configuration example declare 1.1.0. Governance, the operating contract, the delivery lifecycle, the documentation policy and the AI execution rules each declare Version 1.0.0. Templates carry a framework version but no template version. There is no compatibility matrix and no changelog in the kit.

**Why it matters:** The framework requires projects to compare old and new Core on upgrade and to identify breaking changes, but supplies no per-document version history to compare against. A project cannot determine which Core documents changed between kit versions, which makes the prescribed upgrade procedure unexecutable as written.

**Failure scenario:** A project upgrades to a later kit. Core documents still read 1.0.0. The team assumes Core is unchanged, keeps its adapter unchanged, and silently diverges from a rule that did change.

**Recommendation:** Version each Core document independently and ship a CHANGELOG with a Core-document-to-kit-version matrix. Add a "compatible framework versions" field to the Project Adapter.

### F-13 — Parallel status vocabularies across templates and the canonical taxonomy

| **Domain**                | **Severity** | **Type**   | **Required before** |
|---------------------------|--------------|------------|---------------------|
| Governance / Architecture | MEDIUM       | DESIGN_GAP | NEXT_MINOR          |

**Evidence:** The ADR template uses PROPOSED / ACCEPTED / SUPERSEDED, none of which appear in the canonical ARCHITECTURE status set. The Evidence Bundle template offers verdicts spanning two phases (EVIDENCE_READY, EVIDENCE_INCOMPLETE, IMPLEMENTATION_BLOCKED, IMPLEMENTATION_FAILED), so an artifact belonging to the EVIDENCE phase can emit an IMPLEMENTATION status. The Requirement template correctly uses canonical statuses, which makes the inconsistency uneven rather than systematic.

**Why it matters:** The canonical taxonomy is the framework's best asset for future automation. Templates that emit statuses outside it, or that cross phase boundaries, make the work item's true state ambiguous and will be the first thing a state machine chokes on.

**Failure scenario:** An item shows ARCHITECTURE_READY_FOR_APPROVAL in its header and ACCEPTED in its ADR. A second agent reads the ADR, concludes approval exists, and proceeds to Development Analysis.

**Recommendation:** Map every template status to the canonical taxonomy. For the ADR, use the ARCHITECTURE\_\* set and keep SUPERSEDED as a document lifecycle attribute rather than a work-item status. Separate artifact-document lifecycle from work-item phase status explicitly in Governance.

### F-14 — No canonical artifact identity scheme and no artifact graph

| **Domain**   | **Severity** | **Type**         | **Required before** |
|--------------|--------------|------------------|---------------------|
| Traceability | MEDIUM       | TRACEABILITY_GAP | NEXT_MAJOR          |

**Evidence:** Every template carries a free-text "Reference" or ID field. No document defines an identifier convention, a uniqueness rule or the required link set between Requirement, ADR, Development Analysis, ATC, Evidence, Review and Release Record. The example flow uses ATC-CSV-01 as an illustration only.

**Why it matters:** Traceability is currently a naming convention held by whoever writes the artifact. Answering "which requirement caused this production change, and which architecture decision authorised its mechanism" requires manual reconstruction, which is exactly what the evidence principle exists to prevent.

**Failure scenario:** A production defect is traced to a component. Three ATCs touched it. Two reference their parent requirement in prose, one by issue number, and the ADR that authorised the mechanism is referenced nowhere. Root-cause analysis becomes archaeology.

**Recommendation:** Define an ID convention in Core (REQ-\<n\>, ADR-\<n\>, DA-\<n\>, ATC-\<req\>-\<seq\>, EV-\<atc\>, REV-\<atc\>, REL-\<n\>) and a mandatory parent-link set per artifact. Require the Release Record to carry the full chain for each included item. This is the prerequisite for the artifact graph and should precede any orchestration work.

### F-15 — Project Adapter and configuration file overlap with undefined precedence and an incomplete schema

| **Domain**               | **Severity** | **Type**   | **Required before** |
|--------------------------|--------------|------------|---------------------|
| Configuration / Layering | MEDIUM       | DESIGN_GAP | NEXT_MINOR          |

**Evidence:** Both artifacts encode ownership, environments, branch rules, candidate identity, tokens and retry policy. No document states which prevails on conflict; the bootstrap validation step only requires that they not contradict each other. The usage guide states the configuration should contain "enabled gates" and "adapters"; the configuration example contains neither. Review independence, rollback mechanism and project architecture triggers exist in the adapter and have no representation in the configuration.

**Why it matters:** Two partially overlapping configuration sources with no precedence rule is the duplicate-source-of-truth problem the framework warns about, applied to the framework's own configuration. It also blocks enforcement: a validator cannot read gate configuration that has no schema.

**Failure scenario:** The adapter says review must be performed by a different agent; the configuration says independent_review_required: true with no independence field. An agent reads the configuration, satisfies it, and skips the adapter constraint.

**Recommendation:** Declare the configuration file authoritative for machine-readable values and the adapter authoritative for human-readable rules and rationale, with an explicit rule that any value present in both must match and that the configuration wins for automation. Extend the schema with gates, review independence, rollback mechanism, architecture triggers and approval record location.

### F-16 — Two competing templates for the executable unit with no selection rule

| **Domain**          | **Severity** | **Type**          | **Required before** |
|---------------------|--------------|-------------------|---------------------|
| ATC / Documentation | MEDIUM       | DOCUMENTATION_GAP | NEXT_MINOR          |

**Evidence:** AGENT-TASK-CONTRACT.md and EXECUTABLE-TASK.md both define an executable unit with objective, scope, out-of-scope, acceptance criteria, context, dependencies, stop conditions and required evidence. The executable-task template adds the work-item header and context-map fields; the ATC adds approval token, retry limit and parent references. No document states when to use which. The executable task is listed in the manifest but is absent from the README minimum adoption set and from the recommended repository structure in the usage guide.

**Why it matters:** Two templates for one concept invite two parallel practices, and the executable-task template contains no approval token — so choosing it silently omits the approval gate that the ATC carries.

**Failure scenario:** A team adopts EXECUTABLE-TASK.md as its issue template because it contains the canonical header. Work items are created, contexts declared, and implementation proceeds without any APPROVE_TASK_CONTRACT ever being required.

**Recommendation:** Either merge the two — take the ATC as the executable unit and fold the header and context-map fields into it — or state explicitly that the executable task is an issue-tracker presentation of an approved ATC and must carry its reference and approval state. Align the manifest, README and usage guide inventories accordingly.

### F-17 — No cross-cycle limit and no escalation after repeated review or test failure

| **Domain** | **Severity** | **Type**    | **Required before** |
|------------|--------------|-------------|---------------------|
| Execution  | MEDIUM       | CONTROL_GAP | NEXT_MINOR          |

**Evidence:** The retry limit bounds self-correction within one execution (default two cycles). Review remediation is defined as a new implementation cycle and TEST failure returns to DEV for a new candidate, with no cap on the number of such cycles and no trigger that returns the item to Requirement or Architecture.

**Why it matters:** Repeated failure on the same item is a signal about the contract, not about the code. Without a cap, the framework permits unbounded effort on a correctly-executed-but-wrongly-specified item, which is the most expensive failure mode in AI-assisted delivery because each cycle is cheap and plausible.

**Failure scenario:** An ATC fails review three times for acceptance criteria that are mutually inconsistent. Each cycle produces a new implementation, a new evidence bundle and a new review. Nothing escalates; the criteria are never revisited.

**Recommendation:** Define a default cycle budget per ATC (for example, two remediation cycles after review or test failure) and a mandatory escalation on exhaustion: return to Development Analysis or Requirement with a recorded reason. Record cycle count in the Evidence Bundle retry history, which already has the field.

### F-18 — No agent identity, provenance, locking or concurrency control

| **Domain**  | **Severity**                      | **Type**        | **Required before** |
|-------------|-----------------------------------|-----------------|---------------------|
| Multi-agent | MEDIUM (HIGH for multi-agent use) | SCALABILITY_GAP | NEXT_MAJOR          |

**Evidence:** The Evidence Bundle carries a free-text "Executor" field. No document requires recording agent, model, version or session. There is no task locking, assignment semantics, concurrency rule, duplicate-execution detection, handoff artifact or recovery procedure for an abandoned ATC.

**Why it matters:** Provenance of AI-generated change is a basic audit requirement even in single-agent use: if a model version introduced a systematic defect, the framework provides no way to identify which artifacts it produced. Concurrency control is a prerequisite for the multi-agent operation the framework is named for.

**Failure scenario:** Two ATCs from the same analysis touch the same module concurrently. Both pass review in isolation. Integration produces a semantic conflict that neither review could have detected, and no record indicates which agent produced which change.

**Recommendation:** Near term: require executor identity (agent, model, version, session reference) in the Evidence Bundle and a single-active-executor rule per ATC. Medium term: add ATC assignment and locking semantics, a component-level conflict declaration in Development Analysis when slices overlap, and an abandonment rule with a timeout that returns the ATC to an unassigned state.

### F-19 — Lifecycle ends at smoke: no post-release observation, monitoring, SLO or incident model

| **Domain** | **Severity** | **Type**        | **Required before** |
|------------|--------------|-----------------|---------------------|
| Operations | MEDIUM       | OPERATIONAL_GAP | NEXT_MAJOR          |

**Evidence:** The Definition of Done closes at smoke pass and Release Record completion. No document addresses monitoring, alerting, service-level objectives, error budgets, post-release observation windows, operational ownership or incident triage, containment, recovery, root cause and corrective action.

**Why it matters:** Most production defects surface after smoke, not during it. The framework closes the item at the point where operational risk starts, and provides no path by which an operational signal re-enters the delivery process.

**Failure scenario:** A candidate passes smoke and is marked DONE. Error rates rise over the following hours. There is no observation window, no defined owner, no rollback decision point after closure, and the incident is handled outside the framework entirely.

**Recommendation:** Add a minimal post-release observation step to Core: an observation window per release with a named owner and an explicit close, and a defined rollback decision point during that window. Deliver the full operations and incident lifecycle as an Operations Adapter rather than in Core, consistent with the framework's own layering principle.

### F-20 — No decision gate for the case where rollback is not feasible

| **Domain** | **Severity** | **Type**    | **Required before** |
|------------|--------------|-------------|---------------------|
| Release    | MEDIUM       | CONTROL_GAP | NEXT_MINOR          |

**Evidence:** The production failure path prescribes executing the predefined rollback "when applicable". No rule defines what happens when it is not applicable: there is no forward-fix authorisation, no evidence requirement and no decision record, while ad-hoc production patching is prohibited elsewhere.

**Why it matters:** The prohibition and the gap combine badly. Under production pressure, with rollback impossible and forward-fix unauthorised, the framework provides no compliant path — so the actor improvises, and the improvisation is undocumented.

**Failure scenario:** A migration cannot be reversed within the outage window. Rollback is not applicable. The owner authorises a direct fix verbally. Production is changed with no candidate identity, no evidence and no record.

**Recommendation:** Add a FORWARD_FIX authorisation to the lifecycle: permitted only when rollback is demonstrably not feasible, requiring an explicit owner token, a minimum evidence set, a new candidate identity created immediately afterwards, and a mandatory post-incident reconciliation of production state with source identity.

### F-21 — No secure-SDLC controls and no security acceptance gate

| **Domain** | **Severity** | **Type**     | **Required before** |
|------------|--------------|--------------|---------------------|
| Security   | MEDIUM       | SECURITY_GAP | ENTERPRISE_ONLY     |

**Evidence:** Security appears as an architecture trigger, a stop condition and a secrets rule. There is no threat modeling, dependency vulnerability management, SAST, DAST, SBOM, supply-chain control, remediation expectation or formal security acceptance before production.

**Why it matters:** For the declared target users this is a defensible scoping decision and the right layer is an adapter. It becomes a blocker for regulated, customer-facing or enterprise delivery, where security acceptance is a release gate rather than a quality practice.

**Failure scenario:** A dependency with a known vulnerability is introduced within an approved ATC. No control detects it; no gate requires it to be assessed; it reaches production with full process compliance.

**Recommendation:** Publish a Security Adapter defining an optional security acceptance gate before PROD GO, minimum scanning expectations, a dependency introduction policy tied to the existing material-dependency stop condition, and a vulnerability remediation expectation. Keep it out of Core.

### F-22 — No rule on production data in non-production environments and no agent privilege boundary

| **Domain**         | **Severity** | **Type**     | **Required before** |
|--------------------|--------------|--------------|---------------------|
| Security / Privacy | MEDIUM       | SECURITY_GAP | NEXT_MINOR          |

**Evidence:** The lifecycle defines DEV, TEST and PROD roles and states that environment-local runtime data is not promoted as a source artifact. Nothing governs movement in the other direction — production data copied into DEV or TEST — and nothing defines which credentials or environments an executing identity may reach in each phase.

**Why it matters:** Copying production data into test environments is the most common privacy incident in small teams, and it is routine in European contexts where it is also a regulatory exposure. The credential question is sharper still: agents act with whatever access they were given, and the framework assigns none of it to a phase.

**Failure scenario:** To reproduce a defect, an agent restores a production database snapshot into DEV. Personal data now exists in an environment with weaker controls, with no record and no rule broken as far as the framework is concerned.

**Recommendation:** Add two short Core rules: production data may not be copied into non-production environments without an explicit approval and a defined anonymisation or minimisation measure; and the executing identity's reachable environments and secrets must be declared per phase in the Project Adapter, with production access excluded from implementation phases by default.

### F-23 — Bootstrap output has no revalidation trigger or expiry

| **Domain** | **Severity** | **Type**        | **Required before** |
|------------|--------------|-----------------|---------------------|
| Bootstrap  | LOW          | OPERATIONAL_GAP | NEXT_MINOR          |

**Evidence:** Bootstrap produces an adapter, a configuration and a report with a verdict at a point in time. No document defines when bootstrap must be re-run, how gaps recorded as READY_WITH_GAPS are tracked to closure, or what invalidates a previous verdict.

**Why it matters:** Projects change: environments are added, CI is replaced, ownership moves. A stale adapter is worse than none, because it is trusted. READY_WITH_GAPS in particular records accepted risk with no closure mechanism.

**Failure scenario:** A project adopts with READY_WITH_GAPS noting no separate TEST environment. Eighteen months later a TEST environment exists, the adapter still says UNKNOWN, and agents skip independent TEST because the adapter tells them it does not exist.

**Recommendation:** Define revalidation triggers (change of environments, source control, CI/CD, ownership, or framework version) and require each recorded gap to carry an owner and a closure condition. Add "last validated" and "next revalidation trigger" to the Project Adapter.

### F-24 — No gate service expectation and no metrics

| **Domain** | **Severity** | **Type**        | **Required before** |
|------------|--------------|-----------------|---------------------|
| Governance | LOW          | OPERATIONAL_GAP | OPTIONAL            |

**Evidence:** Blocking semantics are well defined (phase-specific status plus Blocked by), but no document defines how long an item may remain blocked, who is accountable for unblocking, or what is measured. The kit defines no metric set.

**Why it matters:** Without any measurement, the framework cannot demonstrate that it improves delivery, and blocked items have no forcing function. This matters most for a consulting or multi-project context where adoption must be justified.

**Failure scenario:** An ATC sits in TASK_CONTRACT_PROPOSED for six weeks awaiting owner approval. Nothing surfaces it; the requirement ages; the analysis baseline goes stale and must be redone.

**Recommendation:** Define a minimal canonical metric set: lead time from requirement to production, ATC cycle time, first-pass review success rate, retries per ATC, architecture escalation frequency, TEST failure rate, rollback rate and blocked time by phase. Add an optional gate response expectation to the Project Adapter.

### F-25 — The translated usage guide duplicates Core and has already drifted

| **Domain**    | **Severity** | **Type**          | **Required before** |
|---------------|--------------|-------------------|---------------------|
| Documentation | LOW          | DOCUMENTATION_GAP | NEXT_MINOR          |

**Evidence:** The Romanian usage guide restates the flow, the architecture triggers, the ATC field set, the evidence content, the review verdicts, the freeze rule, the rollback rules and the documentation layers. Its flow includes a RELEASE READY step absent from the other diagrams and omits the transfer approval. Its list of Core documents not to be modified names five files, while its recommended repository structure names nine.

**Why it matters:** A translated guide that restates rules becomes a second source of truth in a second language, and it has already diverged within one version. Under the framework's own policy it should link rather than duplicate.

**Failure scenario:** A Romanian-speaking team follows the usage guide exclusively. Their process quietly differs from Core, and an auditor evaluating against Core records non-conformance for behaviour the team was told was correct.

**Recommendation:** Reduce the usage guide to adoption steps, worked examples and links into Core. Remove restated rules, flow diagrams and field lists. If full translation is wanted, translate Core itself and version the translation against the Core document version.

### F-26 — Core implicitly assumes a promotable immutable source identity and a review-and-merge model

| **Domain**  | **Severity** | **Type**   | **Required before** |
|-------------|--------------|------------|---------------------|
| Portability | LOW          | DESIGN_GAP | OPTIONAL            |

**Evidence:** Candidate identity defaults to a commit SHA, with alternative immutable artifacts permitted. Branch protection, pull or merge request mechanics and merge strategy appear in the framework configuration and the adapter as expected elements. Bootstrap assumes read access sufficient to inspect repository and delivery tooling.

**Why it matters:** Core is genuinely tool-neutral but not delivery-model-neutral. Low-code platforms, SaaS configuration changes and store-distributed binaries satisfy the immutability requirement only partially, and the framework does not say so.

**Failure scenario:** A team applies AgentFlow to a low-code platform where changes are made in a hosted designer. Candidate identity cannot be established; bootstrap should return BLOCKED, but the adapter fields invite an approximate answer instead.

**Recommendation:** State the applicability preconditions explicitly in the README: a promotable immutable artifact identity, a change-review mechanism, and inspectable delivery tooling. Add guidance for platforms where source identity cannot be promoted, pointing to the alternative immutable artifact rule.

### F-27 — File inventories disagree and convenience copies are unversioned

| **Domain**    | **Severity** | **Type**          | **Required before** |
|---------------|--------------|-------------------|---------------------|
| Documentation | OBSERVATION  | DOCUMENTATION_GAP | OPTIONAL            |

**Evidence:** The README structure tree, the kit manifest and the usage guide's recommended repository structure list different file sets: the manifest includes the bootstrap report template and the executable task template, the README tree omits the bootstrap report template and the manifest itself, and the usage guide omits the executable task template, the adoption guide and the README. Loose convenience copies of documents are distributed alongside the archive and carry no version or status header of their own.

**Why it matters:** Minor individually, but inventory disagreement undermines the kit's own claim to canonical documentation, and unversioned loose copies are the classic origin of an outdated file becoming someone's source of truth.

**Failure scenario:** A project copies a loose bootstrap report template predating a kit update and reports against an outdated gap matrix.

**Recommendation:** Make the manifest the single normative inventory, generate the README tree from it, and stamp every file with a status and framework version header — including templates.

# 13. Independence Requirements

Measures taken to preserve independence:

- The author-produced maturity self-assessment shipped with the kit was read for scope orientation but excluded as evidence. Where its conclusions and this audit's conclusions coincide — notably on the absence of an orchestration engine, enforcement being procedural, and gaps in security, operations and metrics — they were reached independently from Core and template content, and are recorded here as findings with their own evidence.

- This audit reaches conclusions the self-assessment does not: F-01, F-03, F-04, F-05, F-06, F-09 and F-02 are not present in it. These are the findings the auditor considers most material, which is itself an observation about the limits of self-assessment.

- Documentation volume was not treated as evidence of maturity. Several domains are extensively documented and rated MEDIUM on effectiveness for that reason.

- No enterprise mechanism was recommended for Core. Change advisory boards, risk scoring, multi-approver chains and release trains were deliberately excluded and assigned to an organisation adapter, consistent with the framework's stated non-goals.

- The framework was evaluated as a reusable artifact, not as documentation of the project that produced it. No finding depends on knowledge of that project.

Independence concerns identified: the audit is documentation-based. No control could be observed in operation, no completed work item was inspected, and no claim in this report about real-world effectiveness should be read as verified. A follow-up audit against two or three completed AgentFlow work items — from requirement through release record — would raise evidence confidence from MEDIUM to HIGH and is recommended before the framework is presented to third parties as validated.

# 14. Final Audit Conclusion

## Current suitable use

- Solo and small-team software delivery with one accountable owner present at gates.

- AI-assisted development where architecture must be protected against incremental drift.

- Projects with real DEV, TEST and PROD environments and a git-style promotable immutable candidate.

- Existing projects requiring graduated adoption without mass conversion of in-flight work.

- Organisations piloting agent governance before committing to orchestration tooling.

- Consulting engagements needing a defensible, tool-neutral delivery protocol that transfers between clients.

## Current unsuitable use

- Regulated or externally audited delivery, where approval records and evidence must be durable and independently verifiable.

- Multi-team or concurrent multi-agent delivery.

- Production services requiring operational ownership, observation and incident management.

- Autonomous execution with reduced human presence at gates — the context in which the absence of enforcement becomes load-bearing.

- Delivery models without a promotable immutable artifact identity, unless the adapter can establish an equivalent.

## Material blockers

NONE for the declared target use. AgentFlow can be adopted as it stands by a solo or small-team project with an attentive owner, provided the five Immediate items in Section 12 are applied — each is a document-level change of hours to days.

Blockers for other contexts: F-01, F-07 and F-10 for regulated or audited delivery; F-07, F-14 and F-18 for multi-agent operation; F-19 and F-21 for production services at scale.

## Highest-priority improvement

Verifiable evidence (F-01), followed immediately by identity-bound review (F-03). The framework's central promise is that what was executed can be proven; today that promise rests on the executor's own account of its work, reviewed by a party whose independence is undefined, attached to a candidate identity that may since have changed. Closing those three links — artifact-level evidence, defined independence, review bound to the promoted candidate — raises the framework's real assurance more than any amount of new process documentation, and it is a precondition for the enforcement layer that constitutes the next maturity threshold.

## Evidence confidence

MEDIUM. The framework corpus was complete and internally inspectable, so findings about design, coherence, coverage and layering are made with high confidence. No conclusion about behaviour in real execution could be verified, so all effectiveness ratings are design-level only.

## Final notes

AgentFlow is better than its own self-assessment suggests in one respect and weaker in another. It is better as a transferable artifact: the Core/adapter separation is clean, the bootstrap procedure is unusually rigorous for a v1 framework, and the documentation policy solves a real problem that most comparable frameworks ignore. It is weaker on assurance: the self-assessment identifies the missing orchestration engine as the principal gap, but the more immediate exposure is that the evidence and review chain — which the framework treats as already mature — can pass while proving nothing, and nothing in the framework detects when that happens.

The framework's positioning is honest and should be kept: a governance and SDLC protocol for agent-assisted software delivery, not an agentic delivery platform. Nothing in this audit contradicts that positioning. The recommended path to the next level is not more documents; it is fewer, more normative documents plus a minimal enforcement substrate.
